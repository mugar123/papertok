# PaperTok Worker API

This Cloudflare Worker protects provider keys and serves scientific queries, AI, account, institution, notification and share routes.

## Source structure

Wrangler loads `worker/instrumentation.ts`, which reports errors from the Worker, its three bound Durable Object classes and the harvest Workflow to PostHog. The request and schedule implementation stays in `worker/index.ts`. It delegates HTTP requests to `handleRequest(request, env)` in `router.ts`, logs one line for every 429 and 5xx answer (see [Logs](#logs)) and runs the email schedule.

- `router.ts` owns dispatch order, the Origin checks for the feature and health routes (`/health` and `/notifications/unsubscribe` have none), Firebase identity for `PROTECTED_PROVIDER_PATHS`, institution access and `/ai/quota`, a GET-only check for every route after the AI POST routes, and error responses. Most feature handlers check their own methods.
- Provider handlers refuse a disallowed Origin themselves. A request without an Origin passes, except on `/pdf`, which requires one. The `/sources/*` handlers check through `sourceRequestContext` in `provider-runtime.ts`. `/share/*` has no Origin check because it serves crawlers.
- `http.ts` owns JSON responses, allowed Origins and CORS headers.
- `provider-runtime.ts` owns canonical cache keys, provider quota reservations and refunds, the shared OpenAlex budget with its tiers, the harvest's share, observed ceiling and report, the Semantic Scholar beat, the default upstream deadlines and `fetchWithDeadline`.
- `arxiv-api.ts` and `share-route.ts` keep the arXiv beat through `upstream-pace.ts`, and `share-route.ts` reserves its own `share:` ceilings in the request-quota ledger. arXiv, share, the PDF proxy, the citation graph and paper figures set their own deadlines; the PDF proxy and paper figures fetch with their own timers instead of `fetchWithDeadline`.
- `openalex-api.ts`, `citation-graph.ts`, `open-access.ts`, `arxiv-api.ts`, `pdf-proxy.ts`, `semantic-scholar.ts`, `scopus-api.ts`, `physics-api.ts` and `share-route.ts` own their provider handlers. Small source handlers are in `source-api.ts`; health responses are in `health-api.ts`. `openalex-api.ts` also decides which budget tier a relayed request spends, and gives the paper harvest its own entry to the relay (`handleHarvestOpenAlex`).
- The paper corpus (see [Paper store](#paper-store)): `paper-store.ts` owns its rows, lanes, vectors and ranking; `paper-sources.ts` harvests each source by calling the provider handlers above in-process; `paper-enrichment.ts` enriches stored papers; `paper-harvest.ts` runs them as a Workflow; `paper-feed.ts` owns the reader routes.
- Existing feature modules own AI, accounts, institutions, notifications, lists and ledgers.

Provider modules use the shared runtime and HTTP helpers. `http.ts` imports nothing; `provider-runtime.ts` imports `http.ts`, the request-quota ledger and `upstream-pace.ts`. Neither imports the router or a provider module. OpenAlex relay, graph and share requests reserve against the same budget in `provider-runtime.ts`.

## Error monitoring

Set the Cloudflare secret `POSTHOG_PROJECT_TOKEN` to PostHog's public project
token, the same one the frontend uses. An absent token disables reporting, so
local runs report nothing unless `.dev.vars` sets it.

`npm run worker:deploy` requires `POSTHOG_CLI_API_KEY` (a personal API key with
error tracking write access) and `POSTHOG_CLI_PROJECT_ID`, supplied by the
environment or the ignored `.env.posthog-cli`. It bundles the Worker, writes a
PostHog chunk ID into the bundle and its source map, uploads the map under the
current Git commit as release, then deploys that bundle without rebundling. An
upload failure stops the command before deploying. If PostHog is unavailable
and a fix cannot wait, `npx wrangler deploy` deploys without uploading maps;
reports from that release then show bundle locations only.
`npm run worker:deploy:dry-run` packages only and uploads nothing.

Reporting captures exceptions that escape a request, schedule, Durable Object
call or Workflow run, failures the router, rewrites and scheduled delivery catch
and report, and 5xx responses without a reported exception. Expected 4xx failures
are excluded. `src/utils/error-telemetry.ts` reduces each report to the error
type, code locations, release and allowlisted operation, status and email-limit labels, so messages,
requests, user data, paper content and source lines are never sent. Reports have
no person profile and no GeoIP lookup. Backend reporting does not depend on the
browser's analytics choice. PostHog sends no alerts until they are set up in its
error tracking settings; this repository does not configure them.

## Local testing

From the repository root, install dependencies with `npm ci`. Run the Worker with `npx wrangler dev --local --port 8787`; university verification also needs `--local-upstream localhost:8787` (see `POST /institution/verification` below). Local provider credentials belong in the untracked root `.dev.vars` file; never put them in `VITE_*` variables. Local mode emulates KV and Durable Objects, but provider requests still reach live services and can consume quota. The email sender comes from `RESEND_FROM_EMAIL` in `wrangler.toml`, so a real `RESEND_API_KEY` in `.dev.vars` is enough for a local Worker to send real email from the production address against the real Resend quota; set `RESEND_FROM_EMAIL` in `.dev.vars` to use another sender. `--local` also turns off remote bindings, so the Workers AI binding cannot reach Cloudflare: the PDF-to-text conversion for NaN rewrites fails, and NaN is handed the PDF itself (about 45 s to the first token). To test the conversion, run `npx wrangler login` and then `npx wrangler dev --port 8787` without `--local`. Wrangler then runs the AI binding on the Cloudflare account and warns that this may incur usage charges.

For the frontend, copy `.env.example` to `.env.local` and run `npm run dev -- --port 5173` in another terminal. The example points both API variables to `http://localhost:8787`. Firebase web configuration is already in `src/services/firebase.ts`; signing in uses the configured Firebase project.

To use the app with made-up accounts instead of real Google or GitHub sign-in, run `npm run dev:emulators` instead of `npm run dev` (`PORT=5174 npm run dev:emulators` picks another port). It starts the Firebase Auth and Firestore emulators, which need firebase-tools on `PATH` and Java 21 or later (see [`tests/README.md`](../tests/README.md)), and runs Vite in `emulators` mode against them. The app then signs in as `tester@example.com` whenever a page loads with nobody signed in. A new account starts at onboarding. Add `?as=<name>` to any URL, for example `http://localhost:5173/feed?as=alice`, to switch to `<name>@example.com`; the same name always reopens the same account. Guest screens show only between logging out and the next page load, so test them with `npm run dev`. Accounts and Firestore documents stay on this machine and are saved to the untracked `.firebase-emulators/` directory when you stop the command with Ctrl+C. The Worker still checks tokens against the real Firebase project, so routes that require a signed-in user answer 401 for emulator accounts: plain-words rewrites, passage explanations, related papers, the corpus feed, the citation graph, the CORE, physics and Scopus sources, institution access, public lists, notifications and account deletion.

Run the entry-point and routing tests without credentials or live provider calls:

```bash
node --test worker/index.test.ts worker/router.test.ts
```

Before opening a PR, run `npm run check`. It includes the secret scan, lint, knip, TypeScript checks, Node tests, frontend build and Worker dry-run. The build needs the API variables from `.env.local`. A dry-run packages the Worker without deploying it.

### Paper store

The harvest's persisted steps are retry boundaries, not guaranteed new Worker
invocations. CPU can accumulate across category ingestion, enrichment and
embedding until the invocation yields. `wrangler.toml` sets a 120-second active
CPU ceiling instead of Cloudflare's 30-second default: the measured full harvest
needed more than 60 seconds across two exhausted invocations and its remaining
work. This is a script-wide ceiling, including HTTP invocations, so a runaway
request can consume more billable CPU before termination. Provider budgets,
page allowances and retry counts remain separately bounded. Network and storage
waits do not consume active CPU; the step's wall-clock timeout is a different
limit. See [Cloudflare's Workflow CPU limit](https://developers.cloudflare.com/workflows/reference/limits/#increasing-workflow-cpu-limits).


The For You feed reads one paper corpus instead of each source per reader and page. `worker/paper-store.ts` keeps it in D1 (`PAPER_STORE`, database `papertok-paper-store`): one row per paper in the app's `Paper` contract, the identifiers it is known by (`PaperBuilder.identityKeys`), the lanes it can be asked for under, and an int8 vector from Workers AI (`@cf/qwen/qwen3-embedding-0.6b`): the leading 256 of the model's 1,024 dimensions, which it is trained to make an embedding of their own (migration 0004 cut the vectors stored before). A row carries neither `openAlex`, the enrichment's copy of OpenAlex's answer, whose fields the app reads are already merged into the paper, nor `summary`, which repeats `abstract` (`storedPaper`). Enrichment's `rewriteWorks` compares rows in that stored form, so an enrichment that changes nothing leaves the stored paper unwritten. A row an earlier Worker stored keeps both until its next ingest or enrichment rewrites it. The app's library copies, interaction excerpts and RIS export read `abstract` when a paper has no `summary`; an older bundle reads only `summary`, so publish the frontend before deploying the Worker that stops storing `summary`.

A lane is one of the app's categories (`cs.LG`, `bio.gen`, `mech.fluid`), a followed entity (`author:A…`, `institution:I…`, `topic:T…`, `concept:C…`, `query:<text>`, `author-name:<name>`, `project:<funder>|<id>`), the working-paper series (`series:working-papers`) or an area's journal articles (`area:physics`). A paper is filed under the lanes the source that listed it was asked for, its own arXiv categories and the OpenAlex topics it names (`recordLanes`). It is filed under the lane of an OpenAlex author, institution or concept it names only when that lane is in `followed_lanes`: a paper names many of them, readers follow few, and no page reads the rest. Every reader of a category or entity shares its lane, so a paper published before the 90-day window (a liked paper looked up by id, or one a followed lane or specialist source keeps) is filed only under the lanes it was asked for. A follow of an author, institution or concept not yet in `followed_lanes` therefore starts with an empty lane. Once the follow is written there, a paper of the last 90 days that names the entity is filed under the lane when it is next ingested, or when an enrichment changes it. The follow's own harvest lists the entity's papers: the run that `/store/papers` starts at once, for at most 20 new lanes a reader and 2,000 the app a day (`follow-run-lanes:day`, below), or else the nightly refresh (step 4). Such a follow past the 40 lanes a reader, or the 4,000 the app, may write a day (`followed-lanes:day`, below) is not added to `followed_lanes`, so nothing fills its lane until a request within that allowance writes it.

`POST /store/papers` serves it. It requires a Firebase ID token, answers `private, no-store` (the reader's ranking is kept for 15 minutes, below), and counts the per-minute ceilings sized by `PROVIDER_USER_MINUTE_LIMIT` and `PROVIDER_GLOBAL_MINUTE_LIMIT`; it reads only D1, so a ledger that cannot answer lets the request through.
- `{ categories, follows, positiveIds, negativeIds, excludedIds, page, pageSize, order, waitForLikes }` returns `{ papers }`: up to 12 categories and 20 follows, as stored (`{ type, canonicalId, displayName, metadata: { query, funder } }`). The page is ranked by similarity to the closest of up to 24 `positiveIds`: the reader's liked or saved papers, or the one paper they just liked, saved or opened when the app asks for papers related to it. A recency term with a 7-day half-life is added unless `order` is `relevance`; without positive vectors, the base score is recency. Optional `negativeIds` supply up to 24 explicit “not interested” papers. Their maximum cosine only penalizes near copies: above 0.75 it rises linearly to a 0.5 penalty at 1. Missing negative vectors are ignored; rejections never trigger provider lookups or embedding. Optional `excludedIds` supply up to 200 recently viewed or curated paper IDs. Positives, rejections and exclusions resolve through canonical work keys and are removed before pagination. A paper without a vector retains recency. Each paper carries `_fetchedFor`, the asked categories it was found under, and `_followedEntityMatches`, the follows whose lanes hold it. `_semanticScore` carries a request-specific value in [-1, 1]: positive cosine scaled from 0 at 0.4 to 1 at 0.8, minus the rejection signal scaled from 0 at 0.75 to 1 at 1. The client adds it as a separate component bounded at ±100 points; missing scores contribute zero. It is excluded from library records. Asking for any leaf of an area the feed fills from arXiv (physics, mathematics, computer science, economics, finance and the four engineering areas; not statistics, whose label covers OpenAlex's Decision Sciences, mostly operations research and information systems) also reads that area's lane; a paper found only there carries no `_fetchedFor`. Every page uses the same ranked order, with no minimum number of journal, open-access or closed-access papers. Access status contributes no score or diversity adjustment on the client. Papers tied in the ranking take turns between their lanes, each lane's newest first. A request that names follows reads no area lane, even when every follow is a category and so has no lane of its own: its categories stand for followed topics, which the app matches by `_fetchedFor`.
- `seen` and `notable`, optional and sent together, ask for notable papers. `seen` is the papers the reader has seen as the browser's Bloom filter (`feedSeenFilter` in `src/utils/seen-paper-filter.ts`: 19,200 bits, 7 hashes, 3,200 base64 characters whatever it holds; any other value is a 400 `SEEN_INVALID`), and `notable` how many, at most 5 (none without `seen`). A page with papers of its own then adds, after them, up to that many notable papers of the asked categories, published from 1 January ten years before the current UTC year, whose ids the filter does not hold and that the request does not name in `positiveIds`, `negativeIds` or `excludedIds`: ranked as the page is but without a recency term, the closest to the likes first (newest first with no likes). They are not ranks of the page. The app places them on the list as it is when the page arrives, the last card of every 15 since the last notable one whatever size its pages are (`NOTABLE_EVERY` and `joinNotablePage` in `src/utils/feed-enrichment.ts`), and asks for the places of the largest page it can show (`notablePlaces`): the corpus's 15 papers, the follows' 6 and the exploration cards (2 on the first page, up to 10 after it), and 2 spares (`notableRequest` and `NOTABLE_SPARE` in `src/context/feed-notable-cards.ts`). A notable card then keeps its place (`keepNotablePlaces`) when the app re-ranks the cards after the reader, adds the related papers a like brings (`reRankAfterReader` in `src/context/feed-notable-cards.ts`), or takes out a book the reader has not reached, when Crossref answers late (`dropUnreachedPublications`) or a snapshot is restored (`readFeedSnapshot` in `src/context/feed-snapshot.ts`): the next card takes the book's place. Related papers that do not fit before the last notable card follow it, and a notable card that is a book gives its place to the next card, so a place can pass with no notable card in it. The next page places its notable cards again over the other cards after the last notable one, past the cards the reader is on or about to reach (those a re-rank locks: the reader's card and the two after it), so its first notable card takes a place still ahead of the reader; a place among or behind those cards goes to the first card after them, late. A page loads when the reader is two or three cards from the end of the list, so a place the related papers pushed past is usually behind them by then: the reader meets the next notable card 15 + k cards after the last one, k being the cards pushed past its place. A card the reader met still counts after it leaves the list, such as a dismissed card, so the notable cards already listed keep their places. When the reader dismisses a notable card they met, the app keeps the card before it (`notablePlaceAfterDismissal` in `src/context/feed-notable-cards.ts`; the snapshot carries it), and the next page counts from that place. Not interested on another page can take out a card the reader has not reached: as with a book, the next card takes its place (`withoutDismissedCard`). A notable card's place takes the next notable card, and the list's last notable place goes to the next page. That page loads when the reader is two or three cards from the end, so the place is among or behind the cards a re-rank locks, and its first notable card comes late by the cards from that place to the end of the list. A restore keeps the cards the reader met, books included. Only the feed reports the visible card, and the restore runs on every page, so the restore takes the card the reader comes back to from the place FeedContainer keeps for the tab and the account (`forYouScrollKey` in `src/utils/feed-resume-memory.ts`; App clears every place when the account changes); with no place, the reader is on the first card. A snapshot keeps the list's first 30 cards (`FEED_SNAPSHOT_MAX_PAPERS`) for 15 minutes after its page loaded: when the reader left For You past those cards, it is dropped with their place, and For You loads again from its first card; when the account has no snapshot to restore (expired, missing or unreadable), the place goes too. A page still counts its places on the list: after a card the reader met that is not notable leaves it past the last notable place, the page's first notable card comes one card later per such card. The filter does not hold every paper the reader liked, saved, read or dismissed, and `positiveIds`, `negativeIds` and `excludedIds` name at most 24, 24 and 200 of them, so the app drops a notable paper the reader already knows and a spare takes its place. One it does not place is still unseen, so a later page adds it again. A notable card already listed that a book or a dismissed card taken out leaves without a place, at the end of the list, leaves the list: the session that placed it counts it as seen and does not offer it again, and a later session can. Such a card carries `_notable: true` and `_fetchedFor` naming its category, and keeps its own year, citation count and access. Liking, saving or reading one leaves the reader's lean toward older papers as it was (`leanAfterEngaging` in `src/context/feed-temporal-lean.ts`; the page asks for `order: 'relevance'` below -0.3): the card is years old because the feed chose it. A paper of the reader's notable lanes comes only as such a card. The browser sends `seen` and `notable` only with its main page, not with exploration or followed pages; the filter's 3,200 characters count toward the request's 16 KiB, and the rejections and exclusions are trimmed to make room for them. It fills the filter with the papers this session loaded, the last 500 this browser and the account viewed (this browser's list also takes the notable papers the app left out because the reader had liked, saved, read or dismissed them, so later sessions ask past them too), and the last 1,200 notable cards the account viewed (`viewedNotable` in `src/utils/interaction-profile.ts`): the notable papers are offered in one order, so a notable card that only the 500 remembered would come back before any the reader never saw. The filter is used for the page and not stored.
- `{ ids }` returns the corpus's copies of up to 30 papers by the ids the app holds (bare arXiv id, `pmid:`, `openalex:W…` or `W…`, a DOI).
- A follow nobody had asked for is added to `followed_lanes` and harvested at once by a `PaperHarvestWorkflow` instance with `{ lanes }`, which embeds only those lanes' papers, all such runs within 1.5M estimated tokens a day (subject `embedding:follows`; the daily run embeds what they leave). These runs harvest at most 20 of a reader's new lanes a day, and 2,000 of the app's, counted by lane however many one request brings (ledger period `follow-run-lanes:day`, subject `uid:<uid>`); past them the follow is still added, with no error, and the nightly run harvests it. A reader may write 40 lanes a day to `followed_lanes`, new or asked for again, and the app 4,000 (`followed-lanes:day`). A known lane is written again only when it is asked for more than 7 days after its last write, and stays followed for 14 days after each write: the first nightly run that starts more than 14 days after the last write drops it at its eviction step (step 7), or the next night's run if that step fails. A follow nobody asks for any more is therefore dropped 7 to 15 days after its last ask, plus the hours that run takes to reach eviction. Lanes asked for daily are written once a week and spend the app's 4,000 only on the days they fall due. A request reads at most 20 follows, so a reader asking again for their own takes at most 20 of their 40 on a day and still has 20 for new ones. Past the allowance a new follow is not added: the follow of an author, institution or concept has an empty lane until a later request writes it (see the lanes paragraph above), and so does a followed search, an author known by name only or a project, whose lane only its own harvest fills; the follow of an OpenAlex topic is served from what the corpus has. A known lane asked for again once the reader's 40 or the app's 4,000 are spent keeps its last write: the first nightly run more than 14 days after that write drops it unless a later ask within those days is written. One account therefore keeps at most 600 lanes followed: 40 a day over the 15 UTC days a 14-day window touches (step 4 below). Two follows that name one lane count once. When a request brings more lanes to write than an allowance has left, the ones that fit are taken, in the order the follows were sent, by a second reservation for what the refusal reports is left. When the ledger cannot answer for the lanes a reader writes, no lane is written, and a later request writes them: until then a new follow is neither added nor harvested, so the follow of an author, institution or concept, or of a search, a name or a project, has an empty lane, and a known lane keeps its last write. The page is not affected. When only the runs' allowance cannot answer, the follow is added and the nightly run harvests it. A followed lane stays in the nightly refresh until 14 days pass without a write, then is dropped. Which reader asked is not recorded in `followed_lanes`.
- When fewer than three `positiveIds` have a vector, up to ten missing ones are fetched (arXiv for arXiv ids; OpenAlex's single-work lookups, which it does not bill, for PMIDs, DOIs and OpenAlex ids), kept for 30 days (`liked_until`) and embedded within the reader's own 50,000 estimated tokens a day (subject `uid:<uid>` of the embedding ledger) and within 1.5M for all readers together (subject `embedding:readers`, a part of the same reservation), so neither one account nor many can spend the harvest's day. Once the 1.5M is spent, no reader's lookup is embedded until 00:00 UTC: the liked papers it fetched have no vector and do not rank the page (the page is newest first when no liked paper has a vector), and the daily run embeds papers without a vector newest first. A first page of categories does this after it answers, so a lookup never delays the feed's first paint. With `waitForLikes: true`, which the feed sends with the paper just liked, saved or opened when it asks for papers related to it, the page waits up to 1.5 s for it before ranking, so it is ranked by that paper once the paper has a vector (a paper fetched while the 1.5M is spent has none); a lookup still running then goes on after the answer, and the page is ranked by what the corpus has, inside the app's 3.5 s timeout. A request without it, from bundles published before it, gets the lookup after the answer. That lookup waits up to 10 s: the arXiv route's longest wait for a seat (4 s), its upstream deadline (5 s) and a second for its cache read and the beat's ledger calls; `{ ids }` answers inline and waits up to 2 s for the papers it lacks.

Similarity runs in the Worker over at most 4,000 candidates from the asked lanes (the categories, the working-paper series and the follows), an equal share of the newest papers of each, plus at most 800 from the area lanes the request reads, split the same way, so the area lanes take none of a reader's own candidates. The 800-candidate supplement bounds retrieval work without reserving places in the page. Each lane is read with its own statement in one batch (D1 refuses a compound SELECT of more than a few terms). The candidates' vectors are read, in one batch, only when a positive or negative paper has a vector; otherwise the page is newest first. A greedy MMR pass chooses the first 150 ranks from the top 500 candidates, subtracting up to 0.3 for similarity above 0.75 to any previously chosen paper. The remaining candidates retain their base order. Vectors are normalized once per ranking to bound repeated comparison work. The first page keeps the ranked order for 15 minutes in this location's cache, under a key from the verified uid and the request; later pages read only their own papers from it, and rank again when it is gone. The whole order is kept once the work after the answer has run, and only if every followed lane the request asks for had finished its first harvest (`lane_state`) before the page read its candidates, whoever followed it first, that work stored no liked paper or vector, and the order has papers left to serve. Otherwise only the ranks already served are kept: the next page ranks again and goes on after them, so a paper that arrived since starts on that page and no paper already served comes back. The client freezes its exclusion snapshot until a fresh feed load and retains it in the account-scoped feed snapshot across reloads and mode switches. Cache eviction therefore does not remove newly viewed rows before applying the existing page offset. Likes, rejections, the exclusion snapshot and page size enter the cache key. A like or rejection changes the ranking. The order is kept under `store-ranking-v4/`; Worker versions that keep a plain list of ranks use `store-ranking/`, so after a rollback or a deploy neither version reads the other's entries, and a reader's next page is ranked again.

If a fresh load has no client-usable papers or seen fallback after filtering, it restarts once from page zero with an empty exclusion snapshot. This preserves the existing bounded seen-but-unacted-on fallback even when older curated IDs fall outside the 200-ID snapshot. Positive/rejection exclusions and the client’s full curated and known-paper filters still apply; automatic pagination keeps its ten-page ceiling.

The client interleaves recent likes and saves in its 24-positive sample. It requests two exploration papers from nearby categories on the first page, alongside the main and followed requests, with the existing request deadline. Exclusions are limited to 6,000 JSON bytes; the client trims negative IDs first, then exclusions if needed to keep the complete request below 16 KiB. New fields are optional: older clients can call the new Worker, and newer clients accept an older Worker without semantic scores. Deploy the Worker before the frontend to enable all signals. Neither side requires a schema migration.

`/store/feed`, `/recommendations` and `/lists/attribute` are retired. Current
clients use `/store/papers` and link-only public lists. Older bundles must refresh
before the Worker with these removals is deployed.

The `30 2 * * *` cron starts one `PaperHarvestWorkflow` instance per UTC day (`worker/paper-harvest.ts`):
1. Each arXiv OAI-PMH set (`cs`, `math`, `physics`, `stat`, `eess`, `econ`, `q-fin`) from the day in `lane_state`, keeping papers first submitted in the last 90 days, with a 5 s pause between pages and arXiv's `Retry-After` on a 503. A `Retry-After` over 5 minutes, a fourth 503 in a row or a request failing three times ends that set and the ones after it for the run; they start from the same day next time.
2. Every category lane of every other source (`worker/paper-sources.ts`), through the same Worker routes, request builders and mappers the browser used to call per reader: arXiv label searches for the engineering leaves, PubMed for medicine and biology (records with or without an abstract: the query leaves out editorials, letters and comments without one, and ingestion leaves out errata, retraction notices, expressions of concern, news, obituaries, biographies, portraits, interviews and introductory articles by the publication type `PUBTYPE_MAP` gives them), journal articles, with or without an abstract, from OpenAlex's core sources for the 39 leaves of the generated topic map, arXiv's areas included: the 14 accepted in #236 and the 25 the admission gate passes on the 2026-10-23 sample, each asking only for the sampled topics found on target (`openAlexTopicFilterForLeaf`, topic IDs sorted; up to 5 pages a lane, at most 195 of the harvest's 4,000 daily OpenAlex list calls; the map, its evidence and the gate are in `scripts/README-openalex-leaf-topics.md`), the newest articles, with or without an abstract, of the journals (and for computer science, statistics and electrical engineering the proceedings) a labelled sample found on target for each of 80 leaves of physics, mathematics, computer science, statistics, electrical engineering, economics, finance and engineering, filed under the leaf as a topic lane's are (`openalex-venues`, one request a page naming all the leaf's sources, with the type and any topic or author-count filter its sample asked; `openAlexVenueFilterForLeaf` over `worker/openalex-leaf-venues.generated.ts`; up to 5 pages on a lane's first night and 3 after, read whatever their dates since a journal can date a month's issue by its first day, about 133 list calls a night, 240 at most and 152 on the first night, and in step 5 about 33 OpenAlex refresh calls and 96 Crossref type calls a night for their papers; the lists, their evidence, the gate and the leaves without a lane are in `scripts/README-openalex-leaf-venues.md`), the OpenAlex working-paper series, the 200 newest core journal articles, with or without an abstract, of each of the nine areas the feed fills from arXiv other than statistics (`openalex-areas`, by the field or subfields that label a card with the area, `openAlexLabelFilterForArea`, less the working-paper series the review rule lists, which OpenAlex also lists as core journal articles, and for electrical engineering less Biomedical Engineering; one page a night and two on a lane's first run, so 9 list calls a night), bioRxiv, Europe PMC, CORE (3 s between requests: it limits its pace), OSTI, NASA NTRS, NASA ADS or INSPIRE, OpenReview and Hugging Face (`domainSourceRequests`). A lane pages until the source reaches what its previous run had, within a page allowance. A refusal naming a short wait (a minute's ceiling, a pace beat) is waited out, twice at most per page and for 90 s at most per lane, well inside the step's 10-minute timeout; a longer refusal or one past that allowance ends that lane's turn. So does a quota ledger that cannot answer the OpenAlex relay, and one that answers PubMed's minute ceiling with an error. When the ledger's Durable Object cannot be reached, each PubMed and arXiv label-search lane fails on its own without asking its provider; when it answers with an error, `/arxiv` asks arXiv without its pace beat, as it does for readers. Each lane has its own persisted Workflow step and retry boundary; a step that fails past its retries passes over only that lane, which is harvested again the next day. Steps can execute within the same Worker invocation and accumulate its CPU usage; a new step is not a fresh CPU allowance. D1 errors escape the provider-failure handler so the Workflow can retry the lane instead of silently discarding it. A followed lane records its outcome in a separate retried step, so a failed bookkeeping write neither repeats the provider request nor marks unfinished work as served. Exhausted D1 retries leave the lane due for a later run. The OpenAlex topic, venue and area lanes and the series may spend 3,000 of the nightly run's 3,700 OpenAlex units (subject `openalex:harvest:categories`), so the followed lanes' 700 is still there when step 4 starts. PubMed's daily pages hold only days of a large category, so after the initial embedding passes each of its lanes also reads up to 60 pages further back a run, in twelve steps of five to bound the work replayed by a retry, from the page after the last one stored, about 25 pages a minute under PubMed's shared minute ceiling (`backfillLane`, `lane_state.backfill_until` and `backfill_page`, migration 0005). A backfill's listing ends at the day the backfill began, so new records do not move its pages, and the backfill ends at the 90-day window, the end of the listing, the route's last page (100), or once the lane holds the 4,000 papers the feed reads. A refusal past a step's own 90 s of waits, a quota ledger that cannot answer, or a page that fails ends that step at that page, where the lane's next step or run goes on; a step that fails past its retries skips the lane's remaining steps for the run. Scopus is not harvested while `VITE_SCOPUS_ENABLED` is off.
3. Once a week, the notable lane of each of those 39 leaves (`notableLaneJobs`): OpenAlex's 100 most-cited articles from core sources, with or without an abstract, of the leaf's topic filter, published from 1 January ten calendar years before the current year (`from_publication_date:2016-01-01` in 2026, `sort=cited_by_count:desc`). That is one list call a lane, 39 a week, all on the same night, reserved from the 3,000 units the category lanes may spend (step 2); in the nightly run they come right after step 2, whose OpenAlex calls are at most 448 (195 for the topic lanes, 240 for the venue lanes, 9 for the area lanes, 4 for the working-paper series; 160 more on the venue lanes’ first run, 9 more on the area lanes’). A lane is due again seven UTC days after its last harvest; one refused or failed is asked the next night. Its papers are kept whatever their age while the weekly listing renews them, and the embedding pass reaches them after the newer papers. A paper the listing no longer returns leaves the lane 14 days after the last listing that did (`work_lanes.listed_until`, migration 0010), even when a like, its date or another lane keeps it in the corpus. The listing brings OpenAlex's current counts of the papers it returns, so the enrichment's 14-day refresh passes over those the listing files (`renewsEnrichment`) and asks only for one it no longer files (no longer named, or named with a placeholder title the store turns away), however long the corpus keeps it (a recent or liked one); refreshing about 3,900 papers would otherwise add about 39 OpenAlex calls a week. A paper new to a lane gets the first enrichment every new paper gets, which needs no OpenAlex call for OpenAlex's own record but asks Crossref for the type of its DOI (20 DOIs a call: about 195 calls on the first night, a few a week after) and iCite and Europe PMC for one with a PubMed id.
4. Every followed lane written in the last 14 days and not waiting after a failed harvest (below), up to 400, the longest due first: a lane is due from its last harvest or, if it was never harvested, from when it was first followed (`followed_lanes.registered_at`, migration 0007), and among lanes due from the same time the most recently written comes first. They are read from OpenAlex for entities and followed searches (a search is billed as ten list calls), arXiv for authors known by name, OpenAIRE and OpenAlex for projects. Followed lanes may spend 1,000 of the harvest's 4,000 OpenAlex units a day. This nightly refresh has 700 of the nightly run's 3,700, a part with a ledger subject of its own (`openalex:harvest:follows`) that the relay reserves in the same transaction as that share and the day's ceiling (`HARVEST_OPENALEX_PARTS`). The runs new follows start have the other 300 as a share of their own (subject `openalex:harvest:new-follows`, `OPENALEX_NEW_FOLLOWS_DAILY_UNITS`), which nothing in the nightly run spends, enrichment included: a follow added after the run is still harvested at once. They spend from 00:00 UTC, and once their 300 are spent their OpenAlex and OpenAIRE lanes wait for this refresh. Neither spends the other's. Once the 700 are spent, the run's remaining OpenAlex and OpenAIRE followed lanes keep their turn for the next night; each project lane still asks OpenAIRE before OpenAlex refuses it. A refusal is not a turn and adds no wait: a 429 from the ledger (a share, a part, the day's ceiling, arXiv's pace beat), OpenAlex's own 429, which the relay passes on, or a quota ledger that cannot answer an OpenAlex or OpenAIRE lane, which sends nothing to OpenAlex and ends that lane's step. A harvest that fails otherwise is the lane's turn: the lane is due again from the start of the next UTC day, behind every lane harvested before then (`followed_lanes.retry_at`, migration 0007); a hard stop such as a step timeout or CPU limit retries that lane up to twice before recording its next turn. This can repeat provider calls within the existing shared budgets. A D1 failure instead leaves the previous turn unchanged, and the next lane proceeds even if recording an outcome exhausts its own retries. A 5xx, a timeout, arXiv's or OpenAIRE's own 429, a 4xx other than the three below (a 401 or 403 refusing our key or client, a 404), or, for an arXiv author-name lane, a quota ledger that cannot be reached costs the lane that turn and no more, so an outage of any length leaves no wait behind it; a search OpenAlex keeps failing that way spends ten units on each of its turns. When a provider rejects the lane's request itself, with a 400, 414 or 422, each further rejection in a row makes the lane wait longer: 2 nights, then 4, then 7 at most (`followed_lanes.failed_turns`). A search OpenAlex keeps answering with a 400 still spends ten units each time it is asked; from its fourth rejection in a row it is asked no sooner than 7 nights later, then after every lane harvested before that date. A rejection that answers every lane alike, such as a 400 to every search after a change at OpenAlex, leaves each lane it reached waiting; once that is fixed, `npx wrangler d1 execute PAPER_STORE --remote --command "UPDATE followed_lanes SET failed_turns = 0, retry_at = NULL"` gives them their turns back. A harvest clears both columns; `lane_state.harvested_through` moves only on a harvest. While demand stays above the share, a lane can go unrefreshed for more than a day. Asking for a lane again, or following new ones, does not move a lane ahead of one due earlier: the lanes an account follows after another reader's lane was refreshed, however many, wait behind it. Every lane takes its turn, so an account that follows many lanes takes a matching share of the 700 and lengthens every lane's wait. The 40 lanes a reader may write a day bound that: the at most 600 lanes one account keeps followed are about nine nights of the 700 if all are searches. The refresh does not know which account follows a lane, so such an account can still take all of the 700 on a night.
5. Enrichment of new papers (`worker/paper-enrichment.ts`): OpenAlex's citations, topics, authors and access by arXiv id, DOI or OpenAlex id, 25 to 50 a request; iCite and Europe PMC for PubMed ids; Crossref's type for OpenAlex's own records. An OpenAlex or PubMed record without an abstract takes the first one found, in this order: for an OpenAlex record, arXiv's by its arXiv id and INSPIRE's by DOI for a physics paper; then Crossref's, from the calls that bring the OpenAlex records' types (the first of its JATS abstracts, without headings, each formula in its TeX spelling, entities decoded); and Semantic Scholar's from one batch call of up to 500 DOIs a step, which reserves a unit of the `s2` minute ceiling and its one-a-second beat that `/sources/s2` and `/related` share (`/enrich/s2` in `SHARED_MINUTE_CEILINGS`). A record whose type has no abstract (`editorial`, `letter`, `erratum`, `paratext`) is not asked for one, and text shorter than 40 or longer than 6,000 characters is not taken as one (`isPlausibleAbstract` in `src/utils/open-alex-abstract.ts`). A refused reservation sends nothing; a failed source leaves the abstract missing until the 14-day refresh asks again. The feed does not show a book or book review, or a record whose `publicationType` or `sourceType` is `erratum`, `retraction`, `dataset`, `peer-review`, `paratext` or `supplementary-materials` (`isFeedPublication` in `src/services/feed-publication-rules.ts`). Ingestion turns such a record away, and a stored paper leaves every lane once enrichment gives it such a type. A paper OpenAlex does not know yet is asked again after 3, 6 and 9 days. OpenAlex calls spend the nightly run's 3,700 of the harvest's share of the day's ledger (the `feed` tier under **Budget tiers**), whatever the lanes before them left of it, with no part of their own, and never the new follows' 300; a spent share or day leaves the rest for the next run.
6. Each enrichment batch is embedded immediately, by its returned work identifiers, before the next batch is enriched. This avoids waiting for the whole enrichment backlog and avoids embedding an unprocessed paper just before its abstract changes. After enrichment, the run embeds the newest remaining papers without a vector, from their title and abstract, or the title alone for a paper without an abstract, until `EMBEDDING_DAILY_TOKEN_LIMIT` (60M estimated tokens, about 48,000 neurons, ~$0.40 a day past the free 10,000) is reserved. That drains the first backlog in two nights; a day's new papers stay inside the free allocation, and `wrangler.toml` dates the return to 7.5M (2026-10-25). Historical backfill runs after these passes, followed by embedding of its new records. All passes share the same daily budget; there is no access-status priority. Each pass claims the papers it embeds for 10 minutes (`works.embedding_claimed_until`, migration 0006), so passes that overlap (this one, a follow run's, a reader's lookup) never embed one paper twice.
7. Eviction, after embedding: each lane keeps its newest 4,000 papers, the most a page can rank from a category, the series or a follow (a page reads fewer of an area lane's, whose older articles can still be filed under a leaf at step 9); a notable lane drops a paper 14 days after the listing that last returned it; a paper goes once no category lane, notable lane, the working-paper series, an area lane or a lane in `followed_lanes` holds it, or past its keeping date (90 days after publication, 14 days after a specialist source, a notable lane or a followed lane last listed it), unless a reader ranked their feed by it or looked it up in the last 30 days (`liked_until`). A topic lane nobody follows keeps nothing on its own, so someone who follows that topic later starts without the older papers only its lane held, until the follow's harvest lists them. Trimming removes at most 500 memberships from each of ten crowded lanes per step. Eviction then scans 500 work identifiers per step using a primary-key cursor. Each transaction first removes the scanned works' memberships in author, institution and concept lanes not in `followed_lanes`, whether or not the work stays. It then rechecks retention, deletes eligible works and removes their keys, vectors and memberships. The first nightly run after deploying the Worker that files author, institution and concept lanes only for followed entities removes the memberships in unfollowed lanes of those kinds that earlier Workers filed: about 3.4M of the corpus's 4.2M lane rows on 2026-10-24. The workflow saves each cursor, so a failed step resumes without repeating a full-corpus deletion.
8. Thin leaves (`thinLeaves`), after eviction: the step returns every leaf with fewer than 300 papers in its lane published in the last 30 days, fewest first, and stores nothing. `npx wrangler workflows instances describe papertok-paper-harvest harvest-<YYYY-MM-DD>` shows that output; `latest` can name a run for new follows, which has no such step. Propose a listed leaf to the OpenAlex topic-lane gate in `scripts/README-openalex-leaf-topics.md`.
9. Leaf filing (`worker/leaf-filing.ts`), after embedding. A paper of an area lane that a leaf of the area also holds (by its arXiv version's categories or a leaf's own lane) leaves the area lane. In an area with a rule in `LEAF_FILING_RULES`, each arXiv leaf with at least 50 vectors of papers whose primary arXiv category it is gets a centroid, the mean of the newest 500, stored in `leaf_centroids` (migration 0009) in place of the last run's, and a paper whose vector reaches the rule's similarity to its closest centroid, by the rule's margin over the next one, is filed under that leaf instead. No area has a rule until calibration sets one, so no centroid is computed and every other journal article stays at area level. `node worker/test-support/evaluate-leaf-filing.ts <store.sqlite | store.sql>` reports, for each area and candidate rule, how many held-out arXiv papers the rule files and how many of those under their own category, and how many papers of the area's lane it would file.

A new or emptied database needs a harvest before a frontend that reads it is published: apply the migrations, deploy the Worker, start a run with `npx wrangler workflows trigger papertok-paper-harvest`, and wait for its lanes to fill. Until then the feed answers an empty first page with its error and retry.

Records of one paper from several sources merge with `PaperBuilder.merge` into the row any of their identifiers names; the row keeps the id readers already hold. A merge that changes the title or abstract drops the vector for the next embedding pass. The stored row is the base of every later harvest's and enrichment's merge, so it keeps what `merge` records in `sources` about the records it merged (`arxivDoiOnly`, `deniedElsewhere`, `peerReviewedByDoi`, `peerReviewedByDoiComplete`). A row merged before `peerReviewedByDoi` existed lacks its earlier records' entries and has no `peerReviewedByDoiComplete`; nothing is backfilled. Later harvests add their records' entries to such a row. A `false` among them counts, but no `true` among them confirms review, and a merge with such a row does not keep a `true` the way a merge of complete rows does (`repeatsTrue`, `keepsConfirmed`), whether the store merges the row or a browser merges the served copy. Only a row built again from all its records holds every answer; the store never rebuilds a row in place, so such a row stays incomplete until eviction removes it. The first run backfills 90 days of arXiv and each lane's first pages; embedding the backlog takes several daily runs.

When the source a row was built from lists the paper again, as arXiv does with a new version, its title and abstract replace the stored ones; other sources only fill a missing abstract. Hugging Face copies arXiv's title and abstract, so a row it started takes arXiv's new versions and not its own copy. That change drops the vector too. After the arXiv sets, each run copies the vectors of the arXiv-only store (migration 0001) to rows that have none, but only while a row keeps the title and abstract that vector was computed from.

A Worker version from before `peerReviewedByDoiComplete` keeps that mark on a row it merges but files none of the merged record's answers in `peerReviewedByDoi`. A marked row it merges can then lack a record's `false` and read reviewed against it once current code merges the row again. The store does that after current code is deployed again, but browsers do it at once: a Worker rollback leaves the frontend on current code, which merges the rows that Worker serves with other records in search results, followed lanes and OpenAlex enrichment. So remove the mark from every row right after rolling the Worker back to such a version:

```bash
npx wrangler d1 execute PAPER_STORE --remote --command "UPDATE works SET paper = json_remove(paper, '$.sources.peerReviewedByDoiComplete') WHERE json_extract(paper, '$.sources.peerReviewedByDoiComplete') IS NOT NULL"
```

Each row then reads as one merged before the map existed. The older version adds no mark to the rows it merges later, so this one update also covers the next deploy of current code. A harvest that was running at the rollback can still write the mark: if `npx wrangler workflows instances list papertok-paper-harvest` shows one running, run the update again when it ends. A card served before the update can still show from a browser's feed snapshot for up to 15 minutes.

Available routes are `/share/paper/:key`, `/share/list/:shareId`, `/share/entity/:type/:id`, `/share/image/entity/:type/:id`, `/account/delete`, `/institution/link`, `/institution/unlink`, `/institution/services`, `/access`, `/related`, `/store/papers`, `/citation-graph`, `/oa`, `/arxiv`, `/pdf`, `/sources/biorxiv`, `/sources/europepmc`, `/sources/pubmed`, `/sources/s2`, `/sources/core`, `/sources/osti`, `/sources/nasa`, `/sources/physics`, `/sources/scopus`, `/sources/openreview`, `/sources/huggingface`, `/enrich/icite`, `/resources/huggingface`, `/ai/rewrite`, `/ai/annotate`, `/ai/quota`, `/notifications/preferences`, `/notifications/test`, `/notifications/unsubscribe`, `/openalex/*`, `/health/email`, `/health/ai`, `/health/scopus`, `/health/openalex`, `/health/openalex/budget`, and `/health`. The citation graph combines OpenCitations relationships with OpenAlex metadata and caches the result for seven days. `/oa` asks Unpaywall first; when Unpaywall has not indexed a DOI yet (a 404, which is every paper a day old), it reads the Crossref licence instead and answers in Unpaywall's shape with `source: 'crossref'` — only a Creative Commons licence on the version of record (`vor` or `unspecified`) whose `start` has passed counts, so a publisher's text-mining licence or a licence on the accepted manuscript alone does not. A DOI neither can answer for comes back as `source: 'unresolved'` and is cached for six hours; an upstream outage is a 502 and is not cached. The specialist-source routes validate, cache and proxy biology, engineering, physics and AI searches so the browser never depends on public CORS proxies. OpenReview and Hugging Face are keyless discovery sources. NIH iCite enriches up to 200 validated PubMed identifiers per cached batch, while Hugging Face paper details expose associated models and datasets. `/sources/physics` uses NASA ADS when `NASA_ADS_API_TOKEN` is configured and falls back to the public INSPIRE API otherwise. `CORE_API_KEY` is optional; anonymous CORE access remains a best-effort fallback. `/pdf?url=` relays a paper's PDF to the touch-screen viewer, which draws the pages itself with pdf.js because framed PDFs do not work on phones: only the hosts the AI routes already read (arXiv, Europe PMC, PMC) are accepted, redirects are checked against the same list, the body must be a PDF of at most 8 MB, the request must carry an allowed `Origin`, the edge caches a PDF for a day, and the [PDF relay limits](#pdf-relay-limits) count valid GET requests per IP and cache misses globally in one atomic reservation.

`POST /account/delete` deletes the signed-in Firebase account. It is authenticated with a Firebase ID token (no identity cache), uses the Firestore service account, and is safe to retry: each request does one bounded stage (delete the comments and content reports from before comments were removed, drop public lists, follows, clear `createdBy` on paper stubs, profile and handle, the private user tree, newsletter KV, then Auth last). The private user tree includes the saved plain-words summaries (`summaries`) and their history rows (`summaryHistory`); the sweep reads document names only, 80 per request, so a page of summaries is not downloaded just to be deleted. Replies other accounts wrote under a deleted comment stay. Every request also needs a recent sign-in: when the verified token's `auth_time` is missing or more than 240 s old, the route answers 401 `AUTH_RECENT_LOGIN_REQUIRED` before it deletes anything. Identity Toolkit refuses to delete the Auth account for a sign-in that is not recent (`CREDENTIAL_TOO_OLD_LOGIN_AGAIN`), and Auth is the last stage, so without this check that refusal arrived after the data was gone. Firebase does not document its window; it is commonly reported as five minutes. The settings dialog signs the user in again with a popup just before the first request. A deletion that runs past the window stops with the same 401 while `users/{uid}`, the newsletter and Auth are still there, and the next request after a new sign-in continues it. This is a **new** route: deploy the Worker before the frontend.

`POST /institution/link` and `POST /institution/unlink` record the university of the signed-in account on `users/{uid}.institution` (domain, ROR id, display name, acronym, IdP entityID, `verifiedAt`) with the Firestore service account. The proof is checked through Identity Toolkit with no identity cache: the session's own verified address, or, when the account lives on a personal address, a secondary Firebase account's ID token sent as `institutionToken` in the JSON body (16 KB cap) and verified the same way. The address's exact domain is resolved against ROR in one question, and the stored domain is the address's own. A domain ROR lists is found with `query.advanced=domains:<domain>`, matched on the record's `domains`; a website on another domain is no evidence against a record. When several records list the domain, the university (`types` include `education`) is taken, in whatever order ROR returned them, because ROR lists a university's domain under its research units too (ugent.be: the Centre for X-ray Tomography before Ghent University, 2026-10-20); a domain listed under no university links to the first record (ccib.mgh.harvard.edu to a hospital centre). A subdomain is not linked through its parent, because a parent proves no membership: alumni.cmu.edu is alumni mail, mgh.harvard.edu a hospital, and ROR lists the public suffix nhs.uk as two organisations. So an address links only when ROR lists its domain or when the domain is in `CHECKED_MAIL_DOMAINS` (`worker/institution-link.ts`), the student and staff mail domains checked by hand, each with the university page that documents it and the date it was read. An entry names either the university's ROR id, which ROR is asked for by id (`GET /v2/organizations/<id>`: alumnos.uc3m.es is stored as UC3M with ROR's name and acronym, and `/access` finds UC3M's library by that id; such an entry wins over a record ROR lists the domain under, so purdue.edu, which ROR lists only under the Clifford B. Kinley Trust, links to Purdue University West Lafayette), or a domain to ask ROR about instead: neu.edu and husky.neu.edu, the legacy domains of Northeastern in Boston, are asked about as northeastern.edu, because ROR lists neu.edu under Northeastern in Shenyang, and the record must list northeastern.edu. The checked entries also pin Ghent, Sydney, Manitoba, Nevada–Reno, Rochester and LMU (lmu.de) to the university's id (ROR lists each of those domains under a research unit as well, which the university preference now resolves on its own), and cover student mail at ETH Zurich, Edinburgh, Leiden, Sydney, Manitoba, Rochester, TUM (mytum.de) and LMU (campus.lmu.de). `/access` does not read this list. The SeamlessAccess federation metadata is asked for the identity provider's entityID under the address's domain, then under the domain ROR lists for the university (uc3m.es for alumnos.uc3m.es); the entityID stays `null` when the metadata has no entry or is down (husky.neu.edu: Northeastern's provider is listed under neu.edu only). Every registry question of one link shares a 10 s budget (`LINK_LOOKUP_BUDGET_MS`), under the browser's 15 s wait with room for the token checks and the write: a budget that runs out during the ROR question is a 502 `INSTITUTION_LOOKUP_UNAVAILABLE`, never a 404, and no further question is started past it; the federation question is skipped when the budget is gone and the link completes with `entityId: null`. A resolved institution is cached at the edge for seven days (fourth cache generation since 2026-10-20: the first could hold the Shenyang record for neu.edu, the second an institution reached through a parent domain, the third the research unit ROR listed first for a university's domain). The key of a hand-checked domain also names the ROR id or domain its entry asks about, so adding, changing or removing an entry takes effect for that domain at once, while a change to how every domain is resolved still needs a new generation. A domain without a ROR record is a 404 and is not cached; a ROR outage is a 502. The Firestore rules keep the field frozen for the client (`frozenUserFieldsUntouched`), so only these routes ever write or clear it. Both need an allowed `Origin` and use no new secrets. These are **new** routes: deploy the Worker before the frontend.

`POST /institution/verification` accepts `{ email, nonce }` (2 KB cap), requires an allowed `Origin` and a freshly checked Firebase identity whose account has proven its own address (`emailVerified`, or a Google or GitHub identity carrying the same address, the same proof the digest asks for: Firebase flags no GitHub sign-in as verified), and returns only `{ sent: true }`. The nonce is a UUID v4 generated by the browser. The Worker derives `/institution/verify?state=<nonce>` from the request's `Origin`; clients cannot supply a redirect URL. Because the link carries a one-time sign-in credential, the deployed Worker accepts only `https://papertok.app` and `https://www.papertok.app` as that Origin, kept apart because each has its own browser storage and the nonce is in the one that asked. There, the other allowed Origins (the loopback ports, `https://mugar123.github.io` and `https://papertok-ten.vercel.app`) get `403 ORIGIN_NOT_ALLOWED`, so a local frontend cannot finish university verification against the production API. A Worker whose own request URL is on loopback (`localhost`, `127.0.0.1` or `[::1]`) also accepts a loopback Origin. Plain `wrangler dev` rewrites every request URL to the `api.papertok.app` route, so run `npx wrangler dev --local --port 8787 --local-upstream localhost:8787` to test this flow locally. `GET /access?doi=<doi>&domain=<domain>` says whether a reader's library gives access to a paper: `{ status: 'entitled' | 'not-entitled' | 'unknown', collection, url }`. `not-entitled` means the library is not the reader's way in: it lists no full text for the paper, or, for an SFX library, the paper is open to anyone (below). It requires a Firebase ID token (the 60 s identity cache applies) and, when an `Origin` is sent, an allowed one. After validation, an edge-cache miss reserves one unit of the reader's own per-minute allowance in `RequestQuotaLedger`: `ACCESS_USER_MINUTE_LIMIT` per account (120) and `ACCESS_GLOBAL_MINUTE_LIMIT` app-wide (1,000) per UTC minute, kept apart from the `PROVIDER_USER_MINUTE_LIMIT` allowance of related papers and the specialist sources. A cached answer reserves nothing. A refusal is `429 PROVIDER_RATE_LIMITED` with `retry-after: 60`. A missing ledger, or one that answers with an error, is `503 PROVIDER_QUOTA_NOT_CONFIGURED`, and a ledger that cannot be reached is `502 ACCESS_LOOKUP_UNAVAILABLE`. None of these asks a provider, and the card shows no access chip, as on any failure. The DOI follows the `/oa` rule and the domain the institution-link rule; a malformed one is a 400 (`INVALID_DOI`, `INVALID_DOMAIN`). The optional `entityId` (an HTTP(S) SAML entityID such as Manitoba’s `http://CAF.AD.UMANITOBA.CA/adfs/services/trust`, or a URN assigned name such as `urn:mace:incommon:usc.edu`, up to 300 characters) and `rorId` (`https://ror.org/…`) name the institution to GetFTR and are a 400 `INVALID_INSTITUTION_ID` when malformed. When the `GETFTR_API_KEY` secret is set and either id was sent, GetFTR's Entitlement API (`POST /v2.1/entitlements` at `GETFTR_API_URL`, `https://entitlements.prod.getft.io` by default) is asked first: `yes` is `entitled` with its version-of-record link and `collection: 'GetFTR'`, `no` is `not-entitled`, and `maybe`, an unsupported publisher or a GetFTR failure fall through. The library's Alma link resolver comes next, for the institutions in `INSTITUTION_RESOLVERS` (`worker/institution-resolvers.ts`, found by ROR id first and by a domain ROR lists for it second, never by a hand-checked mail domain, since one university answers to several domains; the table is generated by `scripts/diagnostics/alma-resolver-census.mjs`, which finds each library's institution code on its own pages and the Alma region by probing, and keeps only codes that answered): Crossref gives the journal's ISSNs (electronic first, at most two) and year, plus the article's volume, issue and first page, which go to the resolver with the DOI (`rft_id`) so that its link lands on the article rather than the journal's home page (Alma's APS parser reads the DOI, ScienceDirect's the volume and page), and the resolver's `svc_dat=CTO` answer is `entitled` when it lists a full-text service, preferring a subscription over a free one, whose `resolution_url` passes through the university's sign-in. A service Alma itself filtered out (`Filtered`, with a `Filter reason`) does not count, link or not: filtered for the date, it is a collection whose coverage ends before the article (Pau, Nature 2020, until 2012) and the answer is a refusal; filtered for any other reason (an IP range, a user group) it is a service the Worker cannot judge, and the answer is `unknown` rather than `not-entitled`. A library that sends readers straight to one service answers with `available_services` = `single_service` and no `full_text_indicator` at all (Harvard, Helsinki, Amsterdam, 2026-10-19); its services still carry Alma's filter marks, so such an answer is read from what it lists unfiltered: a live service is access, only filtered services is a refusal. A DOI Crossref does not know, a work without an ISSN, or a GetFTR failure with no resolver behind it is `unknown`. A domain with neither provider is a 404 `INSTITUTION_NOT_SUPPORTED`; a Crossref or resolver failure is a 502 `ACCESS_LOOKUP_UNAVAILABLE`, and so is a resolver answer the Worker cannot read: one without a context object, or one whose markup does not hold together, as when it was cut off or lost a tag or a quote (a single-service answer cut off before its services would otherwise read as a refusal, and a `Filtered` key that never closes would count a service Alma filtered out as access). Instead of validating the answer as XML, which took about 1 ms per answer in local Node measurements, the Worker checks its tags in one pass: every `<` starts a tag, a CDATA section or, at the very start, an XML declaration, every element closes inside the one it opened in, the root (`uresolver_content`) closes at the end, a key holds no element and no service opens inside another. The Worker matches tags only as Alma writes them, not in every spelling XML allows: element names without a namespace prefix, each attribute after a single space and in double quotes, with no space around `=` and no `<`, `>` or `&` in its value, no space before a tag's `>` or `/>`, a key with a value opened as `<key id="…">` and a link as `<resolution_url>`; and it reads a service up to the next `</context_service>`, so a service closed in its own opening tag (`<context_service .../>`) is refused too. An answer written otherwise is unreadable: read anyway, a `Filtered` key would count as absent, a full-text service written `service_type='getFullTxt'` would be skipped or lose its link, or a service would be read with the next one's keys. Every saved answer writes its tags this way. CDATA sections are read as literal text before extracting keys, services and links, so a `Filtered` value in CDATA still excludes its service and markup inside a public note cannot become a key or service. Text outside CDATA is not checked, so a complete answer that is not well-formed XML only because of an unescaped `&` is still read. Outside CDATA, only `&lt;`, `&gt;`, `&quot;`, `&#39;` and `&amp;` are decoded; any other reference stays as written, so a `Filtered` value written `&#116;rue` would not exclude its service. The 42 saved answers use only `&lt;` and `&amp;` outside CDATA. One 8 s deadline covers the whole lookup (GetFTR, Crossref and the resolver together), and the browser waits 10 s so a slow answer is still cached by both sides. The answer is the institution's, not the reader's, so it is cached at the edge by the normalized DOI, the library's institution code and the host it is asked on (or the domain when the institution has no resolver; a regional host can answer for a code without the library's data, so a row moved to the library's own host is asked again) and the ids, plus what the resolver was asked about (`citation=article`, so answers from before the article locators were sent are not served on) and how its answer is read (`reading=balanced-tags-cdata`, so answers that counted a filtered service as access, read a cut-off answer as a refusal, or read past a key left open or a tag written another way, are not served on either), for seven days, `unknown` for six hours, and errors not at all. This is a **new** route: deploy the Worker before the frontend.

`GET /institution/services?domain=<domain>` checks publications and publisher platforms for the linked library. It returns `{ services: [{ id, name, publisher, url, monogram, color, collection, ownPlatform, platformId? }], partial, unchecked, remaining, checkedAt }`. Authentication, origins, institution identifiers and provider errors follow `/access`, without its DOI parameter; an `offset` parameter from older clients is ignored. Each request, after validation and before any provider is asked, reserves one unit of an hourly allowance in `RequestQuotaLedger`: `INSTITUTION_SERVICES_USER_HOURLY_LIMIT` per account (30) and `INSTITUTION_SERVICES_GLOBAL_HOURLY_LIMIT` app-wide (600) per UTC hour. The request is counted rather than the probes because one request may probe the resolver dozens of times; a cold library takes the client up to ten requests. A refusal is `429 INSTITUTION_LOOKUP_LIMIT` with `retry-after` set to the seconds left in the hour. A missing ledger, or one that answers with an error, is `503 PROVIDER_QUOTA_NOT_CONFIGURED`, and a ledger that cannot be reached is `502 ACCESS_LOOKUP_UNAVAILABLE`. None of these asks a provider. The client keeps what earlier requests of the same check read as a partial list, or, with nothing read, shows its error state with Retry. The verdicts are kept in the `INSTITUTION_SERVICES_STORE` KV namespace (`wrangler.toml`; `npx wrangler kv namespace create INSTITUTION_SERVICES_STORE` prints the id of a new one): one record per library, keyed by a hash of the parameters the probes are sent with (the resolver's institution code and host, the product, the ids once GetFTR gets them, and how the answer is read), holding a verdict per catalogue entry under the entry's id, ISSN, year, probe DOI and package hint, so a renamed or recoloured entry keeps its verdict and a changed probe is a new entry. A request answers from the stored verdicts and probes only the entries without one: a catalogue that grows costs the entries added, and a reader whose library was read already gets the list at once from any location. Probes run six at a time; no probe starts more than 6 s after the first resolver probe, each request has a 12 s deadline, and the entries no probe started for are `remaining`: the client asks again (up to ten requests in 45 s) and the next request goes on from the store, so a slow library is read in a few requests the first time and once. A probe the deadline cut is `partial` and is not stored, so it is asked again next time; an entry no provider can decide on is `unchecked` and stored as such; a verdict older than 30 days is asked again, and a record nobody asks about for 90 days expires. A request whose probes all failed with nothing in the store is a 502; a missing binding is one too, logged. When every resolver probe of a request failed, that library's resolver is not probed again for 30 minutes in that Cloudflare location, whatever institution ids readers send: a marker in the edge cache, not KV, whose daily writes are few. A request whose GetFTR answer took longer than the start window leaves no marker: GetFTR shares the deadline, so the resolver's probes had less time than a quick request gives them. Until it expires, an entry the store has no verdict for counts as a failed probe without being asked, so the list is `partial`, or a 502 when the store has nothing for the library. Without the marker, every request probed a failing resolver as often as the start window allowed. The answer is `cache-control: no-store`: the store is the cache, and the browser keeps the list in `localStorage` by institution for a day (an hour when partial), so the dialog opens on it. On 2026-10-21 USAL's 198 titles took four pages of 36 and a cold edge cache in every location; the browser kept its copy for five minutes, so every reopen after that started over.

residential address and **9 of 10** from the Worker: without a key, `/sources/s2` and `/related`
are both effectively unavailable, and were before either route existed. The secret was set on

0 of 6 anonymous in the same minutes — so `/health` now reports `semanticScholarKeyConfigured`
alongside `pubmedKeyConfigured`. They are not the same kind of flag: NCBI's absence costs speed,
this one costs the source. A refusal is relayed as a 429 with the provider's own `retry-after`, not
flattened into a 502, so a client can tell a rate limit from an outage; every `/sources/*` route

The key's introductory rate limit is **1 RPS**, and Semantic Scholar applies it per second: of
five requests in one second, one is answered and four refused at once, with no `retry-after`
(measured 2026-09-03). `S2_GLOBAL_MINUTE_LIMIT` (60, shared by `/sources/s2`, `/related` and `/enrich/s2`, the
enrichment's abstract batch) is the same average and no say over which second, so all three
keep a one-a-second beat
(`worker/upstream-pace.ts`): a caller takes the first free second in the shared ledger and sleeps
for it — at most 2.5 s of sleep, which does not count the handful of ledger round trips around it —
and is refused here with `retry-after: 3` rather than upstream when none is free within that budget.
Any gate that refuses — the minute ceiling, the identity quota, the beat, the OpenAlex
budget — gives back every unit an earlier gate had already taken for this request:
`reserveGates` accumulates what each gate takes, and `cacheResponse` refunds all of it on a
refusal. A ledger that cannot be reached between two gates refunds the same units from inside
`reserveGates` itself, which then re-throws so the router still answers with a 502. What is
never refunded is a failed fetch: a timeout is a send the provider received and did not
answer, and the ledger counts sends, not answers.
Derived from the beat's own 2.5 s wait budget rather than written beside it, so the two cannot drift
apart; the router's separate fallback of 2 s for a refusal Semantic Scholar itself sends speaks for
the provider's one-second window and stays as it is.
A refusal Semantic Scholar does send is relayed with the same short wait from both routes;
`/related` used to flatten every failure into a bare 502. Raising the ceiling does not help at
1 RPS — asking Semantic Scholar for a higher limit is what does.
A paper Semantic Scholar has not indexed (its recommendations endpoint answers 404) is not a
failure: `/related` answers 200 `{ recommendedPapers: [], code: 'PAPER_NOT_INDEXED' }` and caches
it for one hour instead of a day, so a newly indexed paper gets its recommendations soon.

`/openalex/*` exists because OpenAlex changed underneath the app. Since February 2026 it requires
an API key and bills each call against a daily budget — $0.10/day anonymous, $1/day on a free key —
so the browser can no longer hold the credential: an OpenAlex key accepts prepaid credit, which
makes a key in the bundle someone else's spending, not just someone else's quota. The route rebuilds
the upstream URL from an entity allowlist and a parameter allowlist, drops any `api_key` the caller
sends, and attaches the Worker's own. It deliberately does **not** require a Firebase identity —
the public entity pages read OpenAlex — so what protects the budget is a pair of global ceilings,
per-minute (`OPENALEX_GLOBAL_MINUTE_LIMIT`) and per-day (`OPENALEX_GLOBAL_DAILY_LIMIT`), reserved
only after an edge-cache miss and for as many calls as the route is about to spend. The origin gate
is not one of them and should not be counted as one: a request with no `Origin` header has nothing
to check, and one is trivially forged, so the ceiling is the frontier. The day matters because the
budget is daily and a per-minute ceiling does not bound it — 3000/min is 4.320.000/day. Every route
that spends the budget reserves against both, in list calls ($0.0001 each): `/openalex/*` for one call, or ten for a search (`search=` or a `.search` filter, billed $0.001, measured 2026-10-20), or nothing for one entity by id or DOI ("Free" on OpenAlex's price list, help.openalex.org/access/example-costs/, read 2026-10-21; the autocomplete endpoint is not on that list and stays one call),
and `/citation-graph` for up to six (its `works/doi:` lookup is one such entity), so a caller who cannot be identified still cannot outspend the
day. A
refusal is relayed with its own status and `retry-after` rather than flattened into a 502 (a stall past the deadline answers `504 UPSTREAM_TIMEOUT`, which the client does not retry, since OpenAlex received and billed the call), and the
rate-limit headers are named in `access-control-expose-headers` so the browser can actually read
them; otherwise the client's backoff falls back to guessing, and since the budget resets at midnight
UTC that guess can be hours wrong. A 404, a work OpenAlex has not indexed, is an answer rather than a refusal and is cached for an hour. `/health/openalex` reports the remaining daily budget in dollars. Its probe is a billed list call outside the day's ledger, limited by the live health probe ceiling described with `GET /health` below.
The edge cache is per data centre, so every location asks OpenAlex the same questions again. On launch day (2026-10-21) the day's ceiling ran out of units while two `/health/openalex` readings showed a quarter of the key's dollars left; that the ledger, not OpenAlex, was refusing is an inference from those readings, not a relay measurement (PAP-86). So an answer is also kept in KV, which every location reads: `NOTIFICATION_STORE` under the `openalex:v1:` prefix, keyed by a hash of the canonical upstream URL, until a namespace of its own exists. A 200 is kept a day, a 404 the same hour the edge keeps it, a refusal or an outage not at all. A miss in one location reads the store before reserving anything, so a question answered anywhere that day costs no units anywhere else. The relay writes KV before the edge cache, treats a failed edge read as a miss and tolerates a failed edge put: the edge cache is not guaranteed inside the harvest's Workflow, and the KV write is what the units paid for. The relay carries no identity, so nothing personal is shared. Identical misses in flight in one isolate share one reservation and one call. A request that arrives while one is in flight joins it at no unit, even when its own tier is closed, and gets what the miss came to, OpenAlex's own refusal included. It does not get the ledger's refusal of the first request's reservation: the harvest and a reader can ask for the same URL under different tiers, so each request that waited on a refused miss starts again under its own tier, one at a time, and the URL still has at most one reservation and one call in flight. Both ceilings are one call to the day's `RequestQuotaLedger` object, which checks the current minute as its subject in the same transaction (the harvest's share instead, and the part of it a lane spends, for the harvest's misses: the new follows' share for a run a new follow started, otherwise the nightly run's), so a reservation is one Durable Object request rather than two. `openAlexCostFor` in `openalex-api.ts` reads the tier from the rebuilt upstream URL, the same one the cache key and the bill come from. It reads no client header or parameter, so a cached bundle gets its tier from what it asks for and one URL always has one tier for a reader. The feed's topic lanes and series are exploration when a reader asks for them: the browser no longer does, and the harvest spends `feed` through `handleHarvestOpenAlex` whatever it asks. Entity lookups cost nothing, reserve nothing and are never refused; the ledger sees them only through the reading their answer files. Tiers rank organic demand. Reader misses also reserve a per-IP allowance of 300 units per UTC minute in the same transaction as the shared minute and daily ceilings, regardless of tier. Networks behind NAT share that allowance; multiple IPs can still spend the shared ceilings. The shares are code, not variables, because changing a variable needs a Worker deploy all the same; retune them from `/health/openalex/budget`. Edge and KV are read before any reservation, so a closed tier still serves stored answers.

Every refusal of the budget, at the minute ceiling, a tier's share or the full ceiling, is the Worker's own `429 { code: 'PROVIDER_RATE_LIMITED' }` with `x-papertok-budget-tier: <tier>`, exposed beside `retry-after`. The browser's OpenAlex client (`src/services/open-alex-client.ts`) fails only that request when the header is there, and closes OpenAlex for the whole tab only on a 429 without it, which is OpenAlex refusing the key. Closing the tab on a tier refusal would stop the opened paper, card enrichment and the free lookups the tiers protect. A closed tier is asked again on the next user action, which costs one Worker request and one ledger transaction, not OpenAlex units. Searches are exploration, so they pause from 60% of the day's ceiling: the search page then says OpenAlex searches are paused and that PaperTok keeps the rest of the day's budget for opening papers and the feed, and the recent-impact score says its request is paused (`isOpenAlexBudgetRefusal`). A bundle without the header check closes OpenAlex for the whole tab on any tier refusal, so once the day passes 60% a refused search would stop the opened paper, card enrichment and the free lookups in that tab for five minutes. **Observed ceiling.** OpenAlex reports the key's day on every answer: `x-ratelimit-remaining-usd` and `x-ratelimit-reset`. The relay files each reading with the day's ledger, free lookups and OpenAlex's own refusals included (`observeOpenAlexBudget`). A reading is what is left, in list calls of $0.0001, less a margin of 200 units (`OPENALEX_OBSERVATION_MARGIN`) for misses already reserved but not yet billed, about twenty searches in flight; the margin is an estimate, not a measurement. The ledger stores the day's usage plus that reading as the observed ceiling, and the latest reading replaces the last. The effective ceiling is the lower of `OPENALEX_GLOBAL_DAILY_LIMIT` and the observed ceiling, so the variable is both a cap and the fallback before the day's first reading or whenever the headers are missing. Spend outside the ledger (the digest, the health probe) and units reserved but never billed stop distorting the ceiling at the next reading, a refusal reporting $0 closes billed misses at once, and credit added mid-day reopens them without a deploy. A reading is dropped when a header is missing or not a number, or when the reset does not end the UTC day the relay reserved under (120 s tolerance), so a reading from yesterday's counter just after midnight cannot close the new day. The relay waits at most 250 ms for the ledger to take a reading (`OPENALEX_OBSERVATION_WAIT_MS`), alongside the KV write, and then answers without it, so a slow or stuck ledger cannot hold a free lookup or the readers sharing its miss; the next answer brings another reading. The citation graph does not take readings, and `/health/openalex` does not file one. Whether OpenAlex still serves free lookups once the key reaches $0 is unverified; the margin keeps the Worker's own traffic from taking it there.

**`/health/openalex/budget`.** One read of today's ledger object through its `peek` action, without spending and without calling OpenAlex. Same Origin gate as `/health/openalex`; a request with no `Origin` passes. Cached at the edge for a minute (`max-age=30, s-maxage=60`). A missing ledger binding is `503 PROVIDER_QUOTA_NOT_CONFIGURED`, an unreachable ledger `503 QUOTA_LEDGER_UNAVAILABLE`, both kept at the edge for ten seconds (`max-age=0, s-maxage=10`), so polling a failing ledger reads it once per location every ten seconds. Its 503s log as `/health/openalex/budget`, apart from the probe's. The body:

```
{ provider: 'openalex', day, resetsAt, unitUsd: 0.0001,
  cap,                    // OPENALEX_GLOBAL_DAILY_LIMIT as parsed
  observedCeiling,        // null until a reading for the day arrives
  observedAt,             // ISO time of that reading, or null
  ceiling,                // min(cap, observedCeiling ?? cap)
  used, remaining,        // remaining = max(0, ceiling - used)
  tiers: { essential | feed | enrichment | exploration: { percent, limit, share, used, refused, open } },  // share: feed only
  kinds: { search | list | graph | share: { used, refused } } }
```

`tiers[tier].used` is that tier's own units; `open` says whether a one-unit miss of the tier would be accepted now (`used + 1 <= limit`, with the whole day's `used`; for `feed` also the nightly run's own units `+ 1 <= share`, its 3,700 of the harvest's 4,000). `feed.used` counts the runs new follows start too, so it can pass `share` while `feed.open` is still true. It counts units, not calls. Entity lookups cost nothing and never appear. The digest's spend shows only through `observedCeiling`. `refused` adds up the units of each miss refused by a tier's share or by the full ceiling, so a closed tier asked again counts again; a refusal by the minute ceiling is a burst, not a closed tier, and is not counted. Nor is a refusal by one of the harvest's two shares, which the ledger checks as subjects like the minute; `feed.open` shows the nightly run's share closing, and the body does not report the new follows' 300. A refusal by a part of the nightly run's share (steps 2 to 4 of the paper harvest) is not counted either, and the body does not report the parts: `feed.open` is for a nightly miss that names no part, such as enrichment's. Units reserved by a Worker deployed before the tiers count in `used` but in no tier. The body carries aggregates only: no subject hashes, minute rows, URLs, ids, queries or users.

`/sources/scopus` does not call Elsevier. `api.elsevier.com` is served by Cloudflare and so is this
Worker, so a subrequest never leaves Cloudflare's network and Elsevier answers it with
`500 GENERAL_SYSTEM_ERROR` — reproduced with a valid key, an invented key, and no key at all, while
the same request from other networks answers normally. Scopus is therefore reached through the Deno
Deploy egress in `proxy/README.md`, which is the only place the Elsevier key lives.

`/health/scopus` measures that whole chain. It runs one minimal search and reports whether the
egress is configured, whether an institutional token is in play, the upstream status, Elsevier's own
error code, the view that answered, whether that view carried an abstract, and the remaining
provider quota — never a key or a token. It tries `COMPLETE`, then `STANDARD`, then the endpoint
default, and records what each one answered, so a failure names which view was refused and why. A
probe costs one upstream call per view it tries, up to three unless `SCOPUS_VIEW` pins one. The
answer is served from the edge cache for ten minutes, and a miss probes only within the live health
probe ceiling described with `GET /health` below: one probe per 10 minutes app-wide, at most 144 a
day. One cached entry serves every allowed origin; the
CORS header is put back for whoever is asking, so a monitor without an `Origin` and a browser with
one no longer cost two provider calls for one answer. Only `COMPLETE` returns `dc:description`, so an
account limited to `STANDARD` produces papers without abstracts.

The AI routes require a valid PaperTok Firebase ID token and keep provider credentials exclusively in the Worker.

Since 2026-10-06 every AI route (`/ai/rewrite`, `/ai/annotate`) answers through NaN Builders, an OpenAI-compatible EU cluster (`AI_PROVIDER = "nan"`, `NAN_API_KEY`, `NAN_MODEL = "deepseek-v4-flash"`); `AI_PROVIDER = "gemini"` switches all of them back to the Gemini models below. Every NaN call turns reasoning off through `chat_template_kwargs`: with it on, a rewrite spent its whole 16,384-token budget thinking and wrote nothing, and `reasoning_effort` is ignored on this model. `deepseek-v4-flash` takes `json_object` but not `json_schema`, so field contracts travel in the prompt. A rewrite hands NaN the paper as text: the Workers AI binding (`[ai] binding = "AI"`, used only for `toMarkdown`) converts the PDF in 1.5–3 s, and the first section arrives a few seconds later (a 15-page paper: first section at about 6 s, complete in about 33 s, measured 2026-10-06). When the conversion fails, NaN is handed the PDF itself, which works but costs about 45 s before the first token. NaN refuses with 402 when the model's monthly token allowance is spent (reported as `AI_QUOTA_EXHAUSTED`, resetting on the first of the month) and 429 at its 60 requests per minute or 7 concurrent requests per model (`AI_BUSY`). `/health/ai` probes only the provider `AI_PROVIDER` names; for NaN it checks that the configured `NAN_MODEL` is served and reports `paperText` for the binding.

With `AI_PROVIDER = "gemini"`, `/ai/rewrite` streams from `AI_REWRITE_MODEL` (or `AI_MODEL` when that is unset) and retries the call that opens the stream once on `AI_FALLBACK_MODEL` when Gemini answers `AI_BUSY`, `AI_UNAVAILABLE` or `AI_QUOTA_EXHAUSTED`. A rewrite the fallback model wrote is stored in the shared cache under the primary model's key for two minutes (`DEGRADED_CACHE_SECONDS`) instead of 30 days, and its `meta.model` names the fallback model, so readers during the outage share it and readers after it get the primary model again. A regenerate the fallback answers is not stored, so it leaves the complete entry already there. The response parser preserves LaTeX commands even when a provider returns raw JSON backslashes.

Rewrite prompt v3 allocates the word budget across the whole document, including
discussion and conclusion. University requests up to 24,000 output tokens; its
previous 16,000-token ceiling cut JWST off before those final sections. The prompt
version is part of the shared cache key, so older shared rewrites are regenerated on
the next open. A summary saved in a reader's account is reopened whatever the prompt
version, until that reader chooses Write it again; it records the version that wrote it.

The reader considers a rewrite complete only after a `done` event whose `sectionCount`
matches the received sections, with no error and no `truncated` flag. EOF alone is not
completion. Interrupted or truncated text remains readable with an incomplete notice
and a retry action, and is not stored in the browser's completed-rewrite cache.
The retry sends `retryIncomplete: true` in the POST body. This bypasses a shared
cache entry only when that entry is marked `truncated`; complete entries remain
reusable. A retry reserves a new quota use and replaces the entry when it produces
a cacheable result. A failed retry leaves the previous partial copy available to
normal opens. Missing, false or non-boolean retry values use the ordinary cache path.

A signed-in reader's complete rewrites are also kept in their own Firestore tree,
written by the browser under owner-only rules: `users/{uid}/summaries/{paperKey}.{level}`
holds the sections, model, source basis and prompt version, and
`users/{uid}/summaryHistory` holds the row the Settings history pages through (paper
key and id, level, title, PDF URL and the server time of the write). Reopening a paper
reads that copy before calling `/ai/rewrite`, so it reserves no use. A read that times
out is not taken as a missing copy: the reader does not call `/ai/rewrite`, and its Try
again reads the copy again. A read the rules refuse goes to `/ai/rewrite` as before copies
were kept, and the result is not saved over the copy that was not read. Writing it again
sends `regenerate: true`, which skips the shared cache read and reserves a use like any
generation. Only a complete result replaces the cache entry and the browser's own copy;
a regenerate cut short leaves both as they were. Missing, false or non-boolean
regenerate values use the ordinary cache path.

`/ai/rewrite` forwards each POST to a new `PaperRewriteSession` Durable Object through
the `PAPER_REWRITE_SESSION` binding. The existing handler verifies identity, validates
input, checks the shared cache and reserves quota inside that object. PDF conversion
and provider stream parsing run there too; the edge Worker only checks method/origin
and relays the response stream. This uses the Durable Object CPU allowance instead
of the Workers Free 10 ms allowance. The object persists no state; the SQLite class
registration keeps it available on the Free plan. Generation still consumes the
account's daily Durable Object request and duration allowances.

Deploy the `v4` migration in `wrangler.toml` before serving this route. A missing
binding returns `AI_NOT_CONFIGURED`; an unavailable session returns `AI_UNAVAILABLE`.
There is no edge-execution fallback. Existing cache, quota, refund, heartbeat and
client-disconnect behavior remains owned by `handlePaperRewrite`.

The Worker limits AI usage per user and globally per UTC day with atomic reservations in the
`RequestQuotaLedger` Durable Object. A reservation is consumed before contacting the provider,
so concurrent tabs cannot exceed the configured limit and failed provider calls fail safely.
Migration `v5` deletes the retired `KimiBudgetLedger` class. The current
`RequestQuotaLedger` remains bound and unchanged.

Routes backed by PaperTok provider credentials (`/related`,
`/citation-graph`, `/sources/core`, `/sources/physics`, and `/sources/scopus`) require a valid
Firebase ID token. They also reserve an atomic per-user and global request allowance per UTC
minute through `RequestQuotaLedger`. Cache keys are built only from validated, output-affecting
parameters, so arbitrary query parameters cannot bypass provider caches.
Authentication is checked before route handling, while quota is reserved only after parameter
validation and a cache miss. Invalid queries and cached responses therefore cannot consume the
provider allowance.

Every route that requires a token also screens it locally before asking Identity Toolkit: three
base64url segments, an unexpired `exp`, and an `aud` matching `FIREBASE_PROJECT_ID` when that
variable is set. Nothing is verified here — the signature check stays with `accounts:lookup` — but
a string that could not have been issued by Firebase no longer costs an upstream call. The screen
runs after the identity cache, which only ever holds verified identities.

Notification routes use this same verifier and its 60-second identity cache,
including the verified display name used in digest greetings. They still require
an email address whose ownership Firebase proves. Invalid credentials remain
`401 EMAIL_AUTH_REQUIRED`, missing configuration is `503 EMAIL_NOT_CONFIGURED`,
and an unreachable verifier is `503 EMAIL_UNAVAILABLE`. Recipient addresses use
the shared verifier’s trimmed, lowercase form.

The publishing routes (`/lists/publish`, `/lists/update`, `/lists/unpublish`)
follow the same rule: each request is validated in full before a unit of the daily publishing
allowance (`PUBLIC_LIST_USER_DAILY_LIMIT`, `PUBLIC_LIST_GLOBAL_DAILY_LIMIT`) is reserved, so a
malformed body cannot consume one. Failures that did reach Firestore still consume theirs, which is
deliberate: they spend a read of the free-tier allowance, and the daily cap is what bounds it.
`/lists/publish` and the merge half of `/lists/update` pin their writes to the document version they
read, and retry once from a fresh read when they lose, so two tabs publishing or syncing at the same
moment can neither orphan a public document nor drop a paper from one. `/lists/unpublish` takes the
private list id from the share record, never from the request body.

Email digests require the `NOTIFICATION_STORE` KV binding, `RESEND_API_KEY`, and `RESEND_FROM_EMAIL` on a verified Resend domain. The Worker verifies the Firebase ID token before storing a subscription, requires the account to have proven the address (`emailVerified`, or a Google or GitHub identity carrying the same address) so nobody can subscribe a stranger's inbox, derives the recipient address from Firebase rather than trusting client input, and sends every digest and unsubscribe page in English (`<html lang="en">`): PaperTok is English-only, so the stored `language` is always `en`, a legacy `language: 'es'` record simply receives English, and the unsubscribe page ignores a legacy `lang` query parameter and `Accept-Language`. Enabled legacy records without follows are marked invalid once and are never sent. A `PUT /notifications/preferences` without `sync` is the reader's own choice: `enabled: false` deletes the subscription and `enabled: true` creates or updates it. The app's background refresh of follows and previews sends `sync: true`, because its tab may have loaded before the reader unsubscribed or changed the digest elsewhere. A sync never creates or re-enables a subscription: it keeps the stored `enabled`, `maxPapers`, `frequency` and `language`, updates only the follows, previews and the verified address and name, and answers with the stored preferences (`enabled: false` when there is no subscription). When those fields are unchanged, a sync writes nothing unless the enabled subscription's unsubscribe token has no `notification:unsubscribe:` index, which happens when a save stored the subscription but lost that write; it then writes only that index, so the unsubscribe link in its digests works.

Resend sends `List-Unsubscribe` and RFC 8058 `List-Unsubscribe-Post` headers on digests, not university verification links. Opening an unsubscribe link with `GET` only shows a confirmation page. The subscription is
deleted by the subsequent `POST` (including RFC 8058 one-click requests), preventing link
scanners and email previews from silently disabling notifications. Every answer on that route is
a page using the email palette (the PT mark and nameplate over the double rule, a serif
headline, one ink action), errors included, and every one carries the same `no-store`,
`no-referrer` and script-free CSP headers, since the token is in the URL. A link that was
already used, replaced by a newer email or cut short answers `400` with a page that sends the
reader to Settings; a missing `NOTIFICATION_STORE` binding answers `503`. The CSP admits no web
fonts, so the page draws the digest's three voices from their local fallback stacks. Preference
request bodies are capped at 96 KiB.

Cron windows run every 20 minutes from 07:00 through 13:40 UTC, every day, so `/health/email` keeps seeing a fresh run. The digest is weekly for everyone since 2026-10: a subscription is due once on a Monday, whatever `frequency` it stored (a record saved as `daily` before the choice was retired is weekly too), and preferences always report and store `weekly`. Tuesday's and Wednesday's windows also reconcile the previous day's ledger. Later windows recover provider uncertainty or retry source failures after 40 minutes and authoritative empty selections after four hours. A digest whose latest attempt this week failed with `EMAIL_DIGEST_SOURCES_UNAVAILABLE`, and that has not been sent this week, may start a new digest on Tuesday only: that failure happens before any delivery is reserved, so nothing can have been sent. A local daily limit or Resend quota rejection holds the selected papers until the next UTC day, including Sunday to Monday. Retries can continue through the following week if later days also reach the limit. If an older edition goes out in a new week, the new weekly selection is tried on the next day. A monthly Resend quota can remain closed until its monthly reset, so the next-day retry is an attempt, not a guarantee of delivery. A short Resend API rate-limit rejection, including a 429 whose body cannot be read, can retry after 40 minutes on the same day and, if needed, on later days through Sunday. The schedule scans on Thursday through Sunday for that backlog. The daily ledger marks its first refused reservation for a PostHog error report, whether the refused send is a digest, a test or a verification email. Resend quota rejections also report an error. Both carry the safe `email_limit: reached` property without recipient data. This repository configures no alert for it: until someone creates a PostHog alert on `$exception` events with `email_limit` = `reached`, nobody is notified when sends are held back. The label is always `schedule`, even when the refused send was a test or verification email. A send whose outcome was uncertain is recovered through its existing reservation instead of starting a new one. Other failures do not start a new digest before the next Monday. The final 13:40 window is recovery-only and never starts a new delivery. Each run has a 12-minute processing budget, keeps three minutes in reserve before starting another three-subscription page, and persists its KV cursor so deferred users resume on the next window instead of starving behind the same users. The digest selects only high-quality, unsent papers from a rolling 10-day publication window; `lastSentAt` controls scheduling but is not a content cutoff. The first quota-refused attempt saves up to ten already selected papers and their source report in the subscriber's generation-scoped delivery state. Daily retries use that selection even if a source is down or a paper ages out. It is cleared on delivery, on a change to follows or paper-count preference, or when a later edition is selected; disabling updates deletes the state. An older held edition that finally sends in a new week leaves the current edition due for the following day. Sent-paper identity history is bounded at 400 keys, enough to cover the window at the maximum configured volume. A scheduled digest with spare capacity may add at most one high-signal exploration paper, but never substitutes exploration when every followed source needed for the selection is unavailable. Test emails remain followed-only.

The email is a single column in the app's light theme: navy ink on warm paper, with the PT mark as its only yellow. A greeting and a headline with the paper count open it, followed by a welcome sentence and a plain line naming the edition's known fields. Each paper sits in its own box with a grey hairline on every side: the lead with an abstract excerpt when available and a button to read it, the rest with their titles and authors. No field, date, venue or citation line appears around a paper. The two reading sections have prominent headings; the second shows its count in parentheses. Discovery papers carry an "Outside your follows" label below their authors. Both buttons end in Phosphor's caret, served as `public/email/caret-right.png` because mail clients strip inline SVG; the frontend must be deployed before a Worker that links to it. The digest's subject names no paper: "Your papers for the week of 19 October", dated by the Monday of the week its papers were selected, so a held edition sent the following week keeps its own week and each week's subject differs. The date at the top of the email is the same selection date. The preheader gives the count and the lead title, which alone is cut at a word boundary. A test email with no papers leaves out the welcome sentence and the closing title. It does not invent a summary of the science or claim that a result is urgent. Each paper carries its field (`area`, one of the twelve `CATEGORIES` keys) and, when its source has one, its abstract: arXiv supplies the primary category and the summary, OpenAlex the subfield or field of the work's `primary_topic` (never the topic's name) and its rebuilt abstract (`usableOpenAlexAbstract`, so an editorial's body is never shown), and the app's preview items carry the card's own `areaKeyForPaper` answer, which the Worker accepts only when it is a known key. A paper of no known field contributes no field name, and one without an abstract leads with no excerpt. The area lookup is imported from `src/utils/area-accent.ts`, which reads the dependency-free `src/data/category-taxonomy.ts` so the Worker bundle carries no React.

Native arXiv topic follows are queried directly in one grouped request, with OpenAlex fallback when arXiv is unavailable. OpenAlex, OpenAIRE, and arXiv requests have bounded timeouts and one bounded retry for rate limits, server failures, or network timeouts. Source attempts, successes, failures, retries, and stable failure codes are recorded without recipient data. An authoritative successful empty response remains an empty outcome; if every usable selection is empty while a required followed source remains unavailable, the run is marked transiently failed instead.

Within one schedule run, identical OpenAlex requests (the date-only exploration query, a followed author, topic, institution or search, a project's DOI lookup) are sent once and their parsed response is shared by every reader who asks. Each reader's relevance filter, follow attribution and sent-paper exclusion still run on that response separately, so no digest changes. The shared requests live only for the run, a failed one is dropped so a later reader retries it with its own bounded retry, and at most 200 answers are kept, past which a request goes upstream unshared. Test emails do not share. Per-source reports therefore separate the questions asked (`attempted`, `succeeded`, `failed`) from the HTTP calls made (`requestAttempts`, `retried`). OpenAIRE and arXiv requests are not shared.

`EMAIL_DAILY_SEND_LIMIT` is enforced by the `EmailDeliveryLedger` Durable Object, using one atomic object per UTC day for scheduled and test sends. The object stores each reservation in its own bounded value plus a small counter, so a full production day remains below Durable Object value limits. Each send reserves quota before provider contact and then commits or releases it. Scheduled reservations and provider idempotency UUIDs are deterministic per subscription generation and UTC day, preventing concurrent cron windows from sending twice while isolating a later resubscription. If a provider response is lost or is not definitively rejected, the exact bounded email draft is retained for one retry between 5 and 25 minutes later; an expired uncertain reservation is conservatively committed rather than risk a duplicate. Committed reservations discard the draft, keep bounded delivery metadata, and every daily object deletes itself after three days. The following day can reconcile a successful provider delivery after a KV write failure without querying scientific sources or sending again, but only while the delivery state has not caught up with the ledger: a reservation whose delivery is already recorded in `lastSentAt` is skipped, so yesterday's committed send cannot swallow today's digest. Provider logs contain only status and stable error codes. The KV emulation of the ledger is serialized only inside one isolate, so it is limited to tests and local runs and requires the explicit `EMAIL_DELIVERY_LEDGER_FALLBACK = "kv"` variable; a deployment with a configured provider and no Durable Object binding aborts the cron with `EMAIL_DELIVERY_LEDGER_MISSING` and reports it in `/health/email` instead of degrading silently.

Subscription preferences and delivery state use separate, generation-scoped KV records with 120-day rolling retention. A quota-held paper selection is part of delivery state and is normally removed on delivery or a relevant preference change; if processing stops, it expires with that record. The separate records mean a scheduled write cannot overwrite a concurrent preference change, recreate a deleted subscription, or contaminate a later resubscription. Schedule summaries remain at `notification:schedule:last-run` and are also written to 14-day `notification:schedule:history:*` keys; each subscription stores separate PII-free digest and test outcomes. `/health/email` returns an unhealthy HTTP status when Resend is unavailable or the configured sender domain is unverified, the latest schedule is stale, or the delivery ledger is not the Durable Object, and exposes only aggregate freshness, processed/deferred/uncertain counts, and stable failure codes, never recipient data. A send-only Resend key cannot list domains, so the probe reports `EMAIL_SENDER_STATUS_UNKNOWN` and returns an unhealthy status until domain verification can be checked. The answer is served from the edge cache for five minutes, and a miss asks Resend only within the live health probe ceiling described with `GET /health` below.

**Live health probes.** `/health/openalex`, `/health/scopus` and `/health/email` call a provider on an edge-cache miss and need no session, and a request without an `Origin` passes. The edge cache is per data centre and nothing joins concurrent misses, so before calling the provider each miss reserves one probe in `REQUEST_QUOTA_LEDGER` for the current UTC window, app-wide: 6 per 10 minutes for OpenAlex, 1 per 10 minutes for Scopus and 6 per 5 minutes for email (Pablo, 2026-10-24). That is at most 864 OpenAlex list calls a day outside its ledger (about $0.09 of the $1 day), 144 Scopus probes and 1,728 Resend domain lists. Once the window is spent, a miss answers `429 HEALTH_PROBE_LIMITED` with `no-store` and a `retry-after` that ends with the window, without calling the provider; the email settings then say the status is unknown instead of unavailable and still let readers turn updates on or off, since saving preferences does not call Resend and a test send reports its own failure. It is a 429 because every 5xx is reported to PostHog (see Error monitoring). Without the binding, or when the ledger answers with an error, no probe runs and the route answers `503 PROVIDER_QUOTA_NOT_CONFIGURED`, also `no-store`; the email settings read that as status unknown too. A refusal is never cached, so the next probe admitted in that location refreshes its entry, and cache hits reserve nothing. Anyone can spend a window, and a location that finds it spent waits for the next one, so a `HEALTH_PROBE_LIMITED` answer says nothing about the provider.

`GET /health` needs no `Origin` and reports configuration, not whether providers answer: `ok`, booleans such as `aiConfigured` and `semanticScholarKeyConfigured` (described above), and `version: { id, tag }` from the `[version_metadata]` binding (`CF_VERSION_METADATA`). `id` is the Cloudflare version id and `tag` is what the deploy passed to `--tag`, or `null` when it passed none. `version` is `null` where the binding does not exist, as in the Node tests.

Workers Logs stores the Worker's `console.*` lines. The per-request invocation logs are off
(`invocation_logs = false` in `wrangler.toml`), because each one would store the request's URL

not say what Free does with lines past that number, so a sparse day in the dashboard does not prove

## PDF relay limits

`GET /pdf?url=` allows 30 valid requests per IP in each fixed UTC minute,
including edge-cache hits. The same `REQUEST_QUOTA_LEDGER` object handles
`api.papertok.app` and any other enabled hostname reaching this Worker. Concurrent requests reserve the caller allowance and the
upstream allowance in one storage transaction, before fetching the PDF. A miss
spends one unit of each; a hit spends only the caller allowance. Misses still
share `PDF_GLOBAL_MINUTE_LIMIT` (120 by default). A failure upstream keeps its
reservation because an attempt was made. Invalid URLs, disallowed Origins,
unsupported methods and OPTIONS preflights spend neither allowance.

The caller identity comes only from `CF-Connecting-IP`, which Cloudflare sets
on ingress. Equivalent IPv6 spellings normalize to the same address. The Worker
computes an HMAC-SHA-256 over the PDF namespace, UTC minute and address using
`PDF_RATE_LIMIT_SECRET`; the quota client hashes this identifier before sending
it to the ledger. The stored counters contain no raw IP, account ID or paper URL.
The identifier changes each minute and is not sent to analytics or logs. Networks
behind NAT share one allowance. Cloudflare Worker subrequests may share a
Cloudflare-provided IP and therefore an allowance too.

The ledger schedules deletion for the end of that minute plus 60 seconds (at
most two minutes after reservation). Cloudflare alarm delays or failures can
retain the expired counters longer; they do not apply to the next minute. The daily OpenAlex and share
ledgers retain the existing three-day cleanup policy. The privacy notice
in [privacy.html](../privacy.html) describes this security processing.

An exhausted allowance returns JSON `PROVIDER_RATE_LIMITED`, HTTP 429,
`Cache-Control: no-store` and a CORS-exposed `Retry-After` with the seconds until
the next UTC minute. There is no HTML challenge. Limits reset at that boundary,
not 60 seconds after the first refusal; up to 60 requests can straddle two
adjacent windows, while no IP can consume more than 30 of either window's
upstream quota. Multiple IPs can still exhaust the shared ceiling. Missing or
invalid IP metadata, a missing/short secret or an unavailable ledger fails
closed, including for edge-cache hits. The reader uses its existing external-PDF
fallback on refusal; closing and reopening it after the reset retries loading.

### Provisioning and verification

Set a dedicated random secret of at least 32 characters before deploying this
handler. Do not reuse a provider key or put it in `VITE_*`. After approval of the
privacy change, provision it without printing it:


shared ceiling stays intact.

## Retired storage and deployment

Migration `0008_remove_unused_harvest_tables.sql` removes `paper_categories` and
`harvest_state`, which the corpus no longer reads. Apply pending D1 migrations
before deploying the Worker. The old `papers` and `paper_vectors` tables remain
because the harvest still imports their records into the corpus.

List publication writes the public document, owner and private pointer atomically.
It no longer writes profile showcases or refreshes legacy pinned cards. Account
deletion still removes stored profile and showcase data. The rules accept a legacy
`onProfile` field so editing an existing list continues to work.

`SCOPUS_VIEW` optionally pins the Elsevier search view to `COMPLETE` or `STANDARD`.
Without it, `scopus-api.ts` tries `COMPLETE`, then `STANDARD`, then the upstream
default for the configured fallback statuses. A pinned view is not retried with
another view. Set it only on the Worker; it does not enable Scopus discovery.


### Production Worker hostname

Production uses `https://api.papertok.app`. `workers_dev = false` disables the
native workers.dev hostname at deployment, and the frontend’s production
allowlist accepts only the custom domain. Local development can still use
localhost or 127.0.0.1. Verify the deployed frontend uses the custom domain
before publishing this setting; older bundles configured with the native host
would lose access to the API. The production bundle inspected on 25 October
2026 configures `https://api.papertok.app`.

## Public lookup caller limits

Public cache misses on `/arxiv`, `/oa`, billed `/openalex/*` requests and
`/share/*` lookups reuse the PDF relay’s `CF-Connecting-IP` normalization and
`PDF_RATE_LIMIT_SECRET`. The HMAC includes the route namespace and UTC minute;
no raw address is sent to the quota ledger, analytics or logs. Configure that
existing secret before deploying these routes. Local requests need a test
`CF-Connecting-IP` header and a secret of at least 32 characters.

| Route | Per IP, per UTC minute | Shared protection |
| --- | --- | --- |
| `/arxiv` | 10 cache misses | Existing one-call-per-three-seconds beat |
| `/oa` | 120 cache misses | No shared quota; Unpaywall and Crossref deadlines still apply |
| Billed `/openalex/*` | 300 units (30 searches or 300 lists) | Existing minute, daily and tier ceilings |
| `/share/*` | 20 uncached lookups | Existing 60/minute and 1,000/day lookup ceilings and provider budgets |

OpenAlex and share attach the caller as the existing reservation’s second
subject, so a refused caller spends no shared quota. Their minute-specific
identifiers expire with the daily ledger’s three-day cleanup. arXiv and OA have
no existing shared reservation: each takes a caller-only reservation, with
cleanup scheduled one minute after the window ends. arXiv gives that unit back
when pacing refuses a seat. Its existing ledger-outage behavior remains
unpaced service; OA, OpenAlex and share do not call their providers if the
quota ledger is unavailable. Missing caller identity or secret refuses lookup
when a caller reservation is required. A share refusal serves the generic
page; other refusals use `429 PROVIDER_RATE_LIMITED` with `Retry-After`.

Edge-cache hits, OpenAlex shared-cache hits and free entity lookups reserve no
caller allowance. In-process paper harvesting uses its existing provider
budgets and pacing without a visitor IP. The public router cannot select those
harvest entry points. Test these paths with `node --test worker/index.test.ts
worker/open-access-route.test.ts worker/paper-feed.test.ts worker/paper-sources.test.ts`.
